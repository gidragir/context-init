# Хранение базы знаний в репозитории (repo storage) — дизайн

Дата: 2026-10-24. Пересматривает решение D1, отменяет D23 (`milestone_decisions.md`).

## 1. Цель

База L0–L2 проекта лежит в самом репозитории, коммитится и используется всей командой:
второй разработчик клонирует репозиторий и сразу получает рабочие MCP/`pack` без `init`.
Обновлять базу может кто угодно — разработчик локально (`context-init update` перед коммитом,
изменения базы в том же PR) или CI/бот; инструмент ничего не навязывает, но любой из способов
даёт тихие, осмысленные диффы.

Сказано пользователем:
- вариант C (обновляет кто угодно), основной сценарий в документации — локальный `update` в PR;
- счётчики строк/токенов не хранить, считать на лету — в обоих режимах;
- legacy `.agents/knowledge` забыть полностью: никакой поддержки, миграции и подсказок;
  проектом пока пользуется только автор, базу можно пересоздать `init`;
- режим по умолчанию — `repo`.

## 2. Конфиг и резолвер

- Новый ключ верхнего уровня `storage = "repo" | "central"`, **по умолчанию `repo`**.
  Источники по D11: `<repo>/.context-init.toml` > глобальный конфиг > дефолт; env
  `CONTEXT_INIT_STORAGE` выше файлов. CLI-флага нет: режим — свойство проекта, не запуска.
  Неизвестное значение — ошибка валидации конфига.
- Пути:
  - `repo` → `<root>/.context-init/knowledge/`;
  - `central` → `~/.local/share/context-init/projects/<project-id>/` (как сейчас).
- `resolve_knowledge_dir(root, storage, central_kb) -> (PathBuf, KnowledgeLocation)`,
  `KnowledgeLocation::{Repo, Central}`. Путь определяется только конфигом, без угадывания
  по наличию файлов.
- `ResolvedProject.is_central: bool` заменяется на `location: KnowledgeLocation`.
- Кэш, телеметрия, feedback остаются централизованными в любом режиме.
- **Подсказка о рассинхроне.** Если активный каталог пуст, а в другом месте (второй режим)
  лежит `L0_index.json`, `check`, `pack`, `update` и MCP-ответы показывают подсказку:
  «база найдена в <путь>, но `storage = <режим>`: запустите
  `context-init migrate --to <другой режим>` или поправьте `.context-init.toml`».
  Ничего автоматически не читается из другого места.

## 3. Удаление legacy

Удаляется всё, что связано с `.agents/knowledge` и корневым `L0_index.json`:
`KnowledgeLocation::LegacyInRepo` и ветки резолвера, `legacy_hint`, перенос
`copy_missing_files` в `init`, legacy-`migrate_knowledge`/`MigrateOptions`/`MigrationReport`,
апгрейд схемы `is_legacy`/`upgrade_to_current`, связанные тесты. Закоммиченный в этом
репозитории `.agents/knowledge/` удаляется. Сам context-init переходит на repo-режим
(dogfooding): база этого проекта коммитится в `.context-init/knowledge/`.

## 4. `migrate` между режимами

`context-init migrate --to repo|central [PATH] [--remove-source] [--dry-run] [--force]`:

- источник — каталог базы противоположного режима, цель — каталог режима `--to`;
- если `--to` совпадает с текущим режимом и база уже там — сообщение «уже в режиме X», код 0;
- нет индекса в источнике — ошибка;
- в цели уже есть `L0_index.json` и нет `--force` — ошибка;
- копирует все файлы базы (включая ручные ADR), проверяет, что `L0_index.json` в цели
  читается, затем записывает `storage = "<--to>"` в `<repo>/.context-init.toml`
  (создавая файл при необходимости и сохраняя прочие ключи и комментарии через `toml_edit`,
  он уже есть в зависимостях бинаря);
- `--remove-source` удаляет источник только после успешной проверки цели;
- `--dry-run` печатает список файлов и ничего не пишет.

## 5. Детерминированный формат (оба режима)

Цель: база в git меняется только при смысловых изменениях — появился/исчез файл или
подсистема, поменялись описание, команды, символы.

- `schema_version` → **3**. Из сериализации убираются `root_path` (L0),
  `files[].lines`, `tokens` (подсистема). В памяти `tokens` остаётся для решений о
  разбиении при детекции (`#[serde(skip)]`), `lines` в `SubsystemFile` удаляется
  или также не сериализуется.
- L1-карточки и `L0_index.md`: без колонки «Строк» и «Объем ~N токенов». Где нужен объём
  (MCP-синтез карточки из L0, `context_get_subsystems`), он считается на лету по текущим
  файлам подсистемы (`count_tokens` детектора).
- Загрузка базы с `schema_version != 3` — ошибка: «база в устаревшем формате
  (schema vN), пересоздайте её: `context-init init --force`».
- **Запись без изменений не происходит.** Генератор рендерит всё содержимое в память и
  пишет файл только если байты отличаются. `updated_at` (дата) меняется только когда
  изменился хотя бы один другой файл базы или иное поле L0; повторный `update` на
  неизменённом дереве не трогает ни одного файла (ни mtime, ни содержимого). Это же
  касается `AGENTS.md`.
- **Стабильный порядок:** подсистемы — по `id`; `files`, `entrypoints`, `key_files`,
  `tags` — отсортированы лексикографически; `key_symbols` — в порядке детектора (это сигнатуры
  в порядке исходника, он детерминирован); JSON — pretty, LF,
  ровно один завершающий `\n`.
- **LLM-резюме:** `update` сохраняет существующие не-шаблонные резюме (уже так) —
  закрепляется тестом: повторный `update` с другим/детерминированным резюме не меняет
  обогащённую подсистему.
- В repo-режиме `init` печатает подсказку добавить в `.gitattributes`
  `.context-init/knowledge/** linguist-generated=true`; файл сам не создаёт.

## 6. AGENTS.md и документация

- Шаблон навигационной секции зависит от режима:
  - `repo`: база лежит в `.context-init/knowledge/` и коммитится вместе с кодом; людям
    можно читать её напрямую, агентам — предпочитать MCP/`pack` (компактнее, учитывает
    бюджет токенов); после структурных изменений — `context-init update` и коммит базы
    в том же PR;
  - `central`: нынешняя формулировка «хранится вне репозитория».
- README, CHEATSHEET: раздел «Хранение базы» (repo по умолчанию, central опционально,
  `migrate --to`, рабочий процесс с PR, `.gitattributes`).
- CHANGELOG (breaking): хранилище по умолчанию — repo; schema v3; удалена поддержка
  legacy `.agents/knowledge`; `migrate` переписан.
- `milestone_decisions.md`: D1 помечается пересмотренным со ссылкой на новое решение
  (база по умолчанию в репозитории, central — опция, кэш/телеметрия централизованы,
  детерминированный формат); D23 — отменено.
- Пользовательские инструкции вне репозитория (запрет читать `.agents/knowledge/**`)
  устаревают; их правка — за пользователем, в итоговом отчёте даётся формулировка.

## 7. Тесты

Все тесты, создающие базы, задают `XDG_DATA_HOME` во временный каталог.

- Конфиг: дефолт `repo`; `storage = "central"` из файла; env выше файла; мусорное
  значение — ошибка.
- Резолвер: путь по режиму.
- Генератор: в L0/L1 нет `root_path`, `lines`, `tokens`; схема 3; повторный `update`
  без изменений не меняет ни одного файла и `updated_at`; изменение файла дерева без
  структурных изменений не меняет базу; порядок отсортирован; ручное резюме переживает
  `update`.
- Хранилище: загрузка схемы 2 — понятная ошибка.
- MCP: синтезированная карточка и список подсистем показывают объём, посчитанный на лету.
- E2E (`tests/cli.rs`):
  - `init` по умолчанию создаёт `.context-init/knowledge/` и ничего не пишет в
    `$XDG_DATA_HOME/context-init/projects`;
  - копия репозитория по другому абсолютному пути отвечает на `pack`/`check` без `init`;
  - `migrate --to central` и обратно, с обновлением `.context-init.toml`, `--dry-run`,
    `--remove-source`, отказ без `--force`;
  - подсказка о рассинхроне режима и данных;
  - `storage = "central"` работает как раньше.

## 8. Вне объёма

- Свой путь каталога (`knowledge_dir`) — не нужен сейчас.
- Автоматическое создание `.gitattributes`, git-хуки, CI-шаблоны.
- Конфликт-резолвер для базы: полагаемся на детерминированный формат и обычный merge;
  после конфликта достаточно `context-init update`.
