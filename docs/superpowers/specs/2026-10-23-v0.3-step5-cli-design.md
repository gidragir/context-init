# v0.3 Шаг 5 — bin `context-init` поверх `ci-*` крейтов (дизайн)

- **Дата:** 2026-10-23
- **Решения:** D1, D11, D16, D19, D21–D23, D29–D31 ([milestone_decisions.md](../../../milestone_decisions.md))
- **Предыдущие шаги:** 1–4 (workspace, `ci-core`, `ci-llm`, `ci-mcp`) — PASS
- **Критерий продукта:** инструмент через любую ИИ собирает документацию проекта (L0–L2) и даёт агентам работать с ней через MCP и CLI с минимумом времени на анализ и токенов. Каждое решение ниже проверяется этим критерием.

---

## 1. Проблема

1. Реальный конвейер анализа (`src/detector.rs` ~2.1k строк, `src/generator.rs` ~0.7k) живёт только в корневом bin. В `ci-mcp` `context_init`/`context_update` — заглушки, пишущие одну подсистему `core` (`crates/ci-mcp/src/handlers.rs:654-750`). MCP-инициализация сейчас бесполезна.
2. Дублирование: `src/mcp.rs` ↔ `ci-mcp`; `src/types.rs` ↔ `ci_core::storage` (почти идентичные `SubsystemInfo`, `ProjectCommands`); AST-сжатие `src/service.rs::compress_rust_ast` ↔ `ci-mcp::handlers::compress_rust_syntax`; `src/ollama.rs` ↔ провайдеры `ci-llm`.
3. bin пишет базу знаний в репозиторий, а не в центральное хранилище (нарушает D1/D23, инвариант хоста №5).
4. Нет команд `config`, `migrate`, `setup`, `telemetry`, `feedback` и флагов `--model`/`--role`.

## 2. Целевая архитектура

```
context-init (bin, тонкий CLI: парсинг аргументов + вывод)
   ├── ci-mcp   (MCP-сервер; handlers вызывают ci-core::analysis + ci-llm::enrich)
   ├── ci-llm   (RoleRouter, провайдеры, + НОВЫЙ модуль enrich)
   └── ci-core  (config, storage, git, telemetry, + НОВЫЙ модуль analysis)
```

Направление зависимостей не меняется: `ci-llm → ci-core`, `ci-mcp → ci-llm, ci-core`, bin → все три. Поэтому `ci-core::analysis` **детерминирован и не знает об LLM**; обогащение — отдельный шаг уровнем выше.

Единый конвейер (используют и CLI, и MCP):

```
analysis::detect(root, opts) -> ProjectAnalysis          // ci-core, детерминированно
  -> enrich::enrich_analysis(&router, role, &mut analysis) // ci-llm, no-op если роль = none
  -> analysis::generate / update(&analysis, &knowledge_dir) // ci-core, пишет в центральное хранилище
```

## 3. Фаза 1 — перенос конвейера, устранение дублей, флаги моделей

### 3.1 `ci_core::analysis`
- Переносятся `src/detector.rs` → `analysis/detector.rs`, `src/generator.rs` → `analysis/generator.rs`, AST-пакер (`pack_builtin_to_string`, `compress_*`, `format_rust_items`, `normalize_rust_tokens`) → `analysis/pack.rs`.
- `src/types.rs`: дубли (`SubsystemInfo`, `SubsystemFile`, `ProjectCommands`, `ProjectType`) удаляются в пользу `ci_core::storage`; уникальные (`ProjectAnalysis`, опции детектора) → `analysis/types.rs`.
- `ci-core` получает зависимости `syn`, `quote` (уже в workspace).
- Генератор пишет L0/L1/L2 в `StoragePaths::project_knowledge_dir(project_id)`. В репозиторий пишутся только `AGENTS.md` (если `with_agents_md`) и навыки — то, что читает харнесс.
- `ci-mcp::handlers::{init, update, pack}` заменяют заглушки/дубли вызовами `ci_core::analysis` (+ `ci_llm::enrich`). `compress_rust_syntax` удаляется.

### 3.2 `ci_llm::enrich` (замена `src/ollama.rs`)
- `enrich_analysis(router: &RoleRouter, role: RoleKind, analysis: &mut ProjectAnalysis) -> Result<EnrichOutcome>`.
- Использует промпты/схемы `ci-llm` для роли (`init` / `update`); при детерминированной роли (`none`) — no-op с `EnrichOutcome::Skipped`.
- Ошибка LLM не валит конвейер: подсистемы остаются с детерминированными summary, в выводе — предупреждение, в телеметрию — `LlmSignal` с классом ошибки.
- Ollama — это просто `[models.<alias>] kind = "ollama"`.

### 3.3 bin
- Удаляются `src/{service,mcp,ollama,detector,generator,types}.rs` и `src/lib.rs`; крейт становится чистым bin.
- `src/main.rs` → `src/cli/` (по модулю на группу команд: `init_update.rs`, `check.rs`, `pack.rs`, `mcp.rs`, `config.rs`, `migrate.rs`, `setup.rs`, `telemetry.rs`), `main.rs` ≤ ~150 строк.
- `#[command(version)]` без литерала (D27).
- `mcp [path]` → `ci_mcp::run_mcp_server(default_root)`.
- `tests/regression_benchmark.rs` переводится на `ci_core::analysis` / `ci_mcp`.

### 3.4 Глобальные флаги (D11, D16)
- `--model <alias>` — алиас из `[models]` для всех ролей этого вызова.
- `--role <role>=<alias>` (повторяемый) — переопределение конкретной роли; приоритетнее `--model`.
- `--config <file>` — явный конфиг-файл (уровень CLI в каскаде D11).
- `--compact` — как сейчас.
- Всё маппится в существующий `ci_core::config::CliOverrides` → `Config::load`.
- **Ломающее изменение:** `--ai`, `--ollama-url`, `-m/--model <имя модели ollama>` у `init`/`update` удаляются. При их использовании clap выдаёт ошибку; в `README`/`CHANGELOG` — таблица миграции (`--ai -m qwen` → `[models.local] kind="ollama" model="qwen"` + `--model local`). Детерминированный режим — по умолчанию (роль без алиаса = `none`), что дешевле по токенам и предсказуемо.

## 4. Фаза 2 — `config` и `migrate`

### 4.1 `config` (D11)
| Подкоманда | Поведение |
| :--- | :--- |
| `config init [--project] [--force]` | Пишет закомментированный шаблон в глобальный (`~/.config/context-init/config.toml`) или проектный (`<repo>/.context-init.toml`) путь через `Config::init_config_file`. Существующий файл без `--force` — ошибка. |
| `config show [--json]` | Эффективный (слитый) конфиг + список реально загруженных источников по приоритету. |
| `config path` | `StoragePaths::format_paths(project_id)`: глобальный конфиг, проектный конфиг, data dir, папка знаний проекта, телеметрия. |
| `config validate` | Загружает каскад и проверяет: алиасы в `[roles]` существуют в `[models]`; `kind` валиден; `endpoint` парсится как URL для сетевых провайдеров; `max_response_tokens >= 64` (ниже — футер пагинации не помещается, см. ci-mcp_summary §4.3). Выход `1` при ошибках, все ошибки списком. |

Проверка `max_response_tokens >= 64` дублируется в `Config::load` как предупреждение (не ошибка), чтобы MCP-сервер не падал на старом конфиге.

### 4.2 `migrate [path] [--remove-source] [--dry-run] [--force]` (D23)
- По умолчанию **копирует** `.agents/knowledge` в центральное хранилище, источник сохраняется (обратимо; при наличии центральной копии in-repo не читается — D21 lazy fallback).
- `--remove-source` — удалить источник после успешной копии.
- `--dry-run` — список файлов и путь назначения, без записи.
- Обёртка над `migrate_in_repo_knowledge_with_options`; вывод — `MigrationReport`.
- Если центральная копия уже есть: без `--force` — ошибка с подсказкой (не перезаписываем молча).

## 5. Фаза 3 — `setup <harness> [--write]` (D22)

### 5.1 Поведение
- Регистрация **только на уровне пользователя**: один глобальный сервер (D21) сам определяет проект через `roots`/cwd; проектные файлы дублировали бы одну запись в каждом репо.
- Без `--write`: печатает целевой файл и unified diff предлагаемых изменений. С `--write`: бэкап `<file>.bak.<YYYYMMDD-HHMMSS>` → слияние → запись. Нет изменений → нет записи и бэкапа (идемпотентно).
- Слияние меняет **только** ключ `context-init`, остальное сохраняется: JSON — `serde_json` с `preserve_order`; TOML — `toml_edit` (сохраняет комментарии). Невалидный исходный файл → ошибка, файл не трогаем.
- `command` = абсолютный путь `std::env::current_exe()`, `args = ["mcp"]` (GUI-харнессы не наследуют PATH оболочки).
- `setup all [--write]` — по всем харнессам, чей каталог конфигурации существует.

### 5.2 Таблица харнессов (данные в одном модуле `setup/harness.rs`)
| Харнесс | MCP-файл | Формат / ключ | Правило/навык |
| :--- | :--- | :--- | :--- |
| `claude-code` | `~/.claude.json` | JSON `mcpServers.context-init` (`type: "stdio"`) | `~/.claude/skills/context-init/SKILL.md` |
| `claude-desktop` | Linux `~/.config/Claude/claude_desktop_config.json`; macOS `~/Library/Application Support/Claude/…`; Windows `%APPDATA%\Claude\…` | JSON `mcpServers.context-init` | — (нет механизма правил) |
| `cursor` | `~/.cursor/mcp.json` | JSON `mcpServers.context-init` | Печатается текст для User Rules (хранятся в UI, не в файле) |
| `gemini-cli` | `~/.gemini/settings.json` | JSON `mcpServers.context-init` | Блок в `~/.gemini/GEMINI.md` |
| `antigravity` | `~/.gemini/config/mcp_config.json` (проверено на хосте) | JSON `mcpServers.context-init` | Блок в `~/.gemini/GEMINI.md` |
| `codex` | `~/.codex/config.toml` | TOML `[mcp_servers.context-init]` | Блок в `~/.codex/AGENTS.md` |

- Блоки правил ограничены маркерами `<!-- context-init:begin -->` / `<!-- context-init:end -->`; повторный `setup` заменяет блок, а не дописывает. Общий файл `GEMINI.md` у gemini-cli и antigravity безопасен благодаря маркерам.
- Текст правила — один шаблон ≤ 15 строк: MCP-first (`context_get_subsystems` → `context_get_subsystem` → `context_pack`), CLI-fallback `context-init pack <id> --compress` для субагентов (D31), `context_check` перед сдачей. Короткий текст = меньше токенов в каждом системном промпте.
- Домашний каталог берётся из инъецируемой структуры `HomeDirs` (в тестах — tempdir).

## 6. Фаза 4 — `telemetry` и `feedback` (D29, D30)

- `telemetry report [--month YYYY-MM] [--notes]` → `render_telemetry_report` в stdout (md + YAML front matter). Телеметрия выключена (opt-in, дефолт `false`) и событий нет → сообщение, как включить (`[telemetry] enabled = true`).
- `telemetry report --submit [--yes]`: показывает дайджест и спрашивает подтверждение (`--yes` пропускает). Если `gh` доступен и авторизован → `gh issue create -R gidragir/context-init --label telemetry --title "telemetry: <YYYY-MM>" --body-file <tmp>`. Иначе печатает предзаполненную ссылку `https://github.com/gidragir/context-init/issues/new?labels=telemetry&title=…&body=…` (тело обрезается до ~6k символов с пометкой). Заметки (`note`) по умолчанию не включаются (O6).
- `feedback <tool> <verdict> [--note <text>]` → `FeedbackSignal` через `JsonlTelemetrySink`, поведение идентично MCP `context_feedback` (уважает `telemetry.enabled`; при выключенной — сообщает, что не записано). `verdict` — свободная строка, подсказка в `--help`: `helpful|unhelpful|accurate|stale`.

## 7. Обработка ошибок
- Все команды возвращают `anyhow::Result`; выход `1` + одна строка ошибки с контекстом (в `--compact` — без цветов/баннеров).
- Файловые записи вне хранилища (`setup`, `config init`) — только после успешной сборки нового содержимого в памяти; бэкап до записи.
- Деструктивное (`migrate --remove-source`) — только после успешной копии и сверки числа файлов.

## 8. Тестирование
- Перенос конвейера: существующие тесты detector/generator переезжают в `ci-core`; `regression_benchmark` должен проходить с теми же метриками (сравнение с `reports/benchmark_latest.json`).
- `ci-mcp`: тест, что `context_init` на фикстуре даёт > 1 подсистемы (регрессия против заглушки).
- `enrich`: мок-провайдер (`RoleRouter::with_registry`) — успех, `none` → Skipped, ошибка провайдера → детерминированный результат + предупреждение.
- CLI: интеграционные тесты через запуск бинаря с `HOME`/`XDG_*`/`CONTEXT_INIT_*` на tempdir.
- `setup`: для каждого харнесса — отсутствующий файл, файл с чужими серверами, файл с нашей устаревшей записью, невалидный файл (ошибка, без записи), идемпотентность (без бэкапа при повторе), сохранение комментариев TOML.
- `config validate`: по кейсу на каждое правило. `migrate`: copy / `--dry-run` / `--remove-source` / уже мигрировано.
- `telemetry --submit`: `gh` подменяется через `PATH` на скрипт-заглушку; ветка без `gh` проверяет ссылку. Реальные issue в тестах не создаются.

## 9. Гейт приёмки
1. `rtk cargo check --workspace`, `rtk cargo clippy --workspace --all-targets -- -D warnings`, `rtk cargo nextest run --workspace` — зелёные.
2. `rtk rg -i '1[cс]'` по коду — 0 упоминаний продукта.
3. `context-init check` на самом репозитории — без дрейфа; `context-init init` на репозитории пишет в центральное хранилище и даёт ≥ подсистем, чем текущий `L0_index.json`.
4. Ручной smoke: `setup claude-code` (dry-run diff), `config validate`, `migrate --dry-run`, `telemetry report`.
5. Отчёт `reports/subagents/context-init_verification.md` от независимого верификатора.
