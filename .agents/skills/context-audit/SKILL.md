# context-audit: Регулярный аудит регрессий и бенчмаркинг

Данный навык регламентирует регулярный запуск сквозных автотестов, проведение замеров латентности и степени сжатия кода, а также формирование отчетов для отслеживания прогресса разработки `context-init`.

---

## ⚡️ Когда активировать навык

Выполнять процедуру аудита:
1. При любых изменениях логики в модулях `detector.rs`, `generator.rs`, `mcp/`, `service.rs`, адаптеров языков `lang/`.
2. Перед созданием коммита или выпуском релиза `context-init`.
3. При подключении новых монорепозиториев хоста для валидации совместимости и замеров токенов.

---

## 🚀 Пошаговый протокол выполнения

### Шаг 1. Запуск регрессионного бенчмарк-комплекса

Выполнить запуск тестов в режиме `--release` с фиксацией вывода:

```bash
CONTEXT_INIT_WRITE_BENCHMARK=1 rtk cargo test --release --test regression_benchmark -- --nocapture
```

Тестовый набор автоматически выполняет:
- **Замер латентности Drift Audit:** 10 последовательных итераций проверки дрейфа на репозитории.
- **Замер эффективности AST-сжатия:** парсинг AST синтаксиса `syn`, вырезание тел функций до `⋮----` и подсчет сэкономленных токенов tiktoken (BPE).
- **Сквозной аудит всех инструментов MCP:** поочередный вызов `context_init`, `context_check`, `context_get_subsystems`, `context_pack`, `context_update` в изолированном пространстве.
- **Кросс-проектный тест:** валидация работы со структурой базы знаний.
- **Генерация отчетов:** автоматическая запись артефактов в `reports/BENCHMARK_REPORT.md` и `reports/benchmark_latest.json`.

---

### Шаг 1.1. Точный BPE-замер эффективности на монорепозиториях хоста

Для верификации экономии токенов на реальном проекте (например, `mimir`):

1. **Запуск замеров по подсистемам:**
   Используется Python с BPE-токенизатором `cl100k_base` (`/home/gidragir/.local/share/uv/tools/headroom-ai/bin/python`):
   ```bash
   # Замер raw vs comp
   rtk context-init pack <id> <repo_path> --no-compress
   rtk context-init pack <id> <repo_path> --compress
   ```
2. **Критерии качества сжатия:**
   - Кодовые модули (> 1k токенов): экономия токенов $\ge 45\%$.
   - Навигационный индекс L0: сокращение нагрузки $\ge 95\%$ относительно полного дерева проекта.
3. **Замер латентности дрейфа (10 итераций):**
   ```bash
   rtk context-init check <repo_path> --compact
   ```
   Целевой порог: `< 150 ms` для проектов до 500 файлов.

---

### Шаг 2. Контроль порогов и предотвращение деградации

Проверить сгенерированный отчет в `reports/BENCHMARK_REPORT.md`:

| Параметр | Целевой порог | Действие при превышении |
| :--- | :--- | :--- |
| **Drift Audit Latency (local)** | `< 25.0 ms` | Проверить избыточные файловые сканирования в `detector.rs` |
| **Drift Audit Latency (monorepo)** | `< 150.0 ms` | Оптимизировать git статус и файловый обход |
| **AST Compression Ratio (code)** | $\ge 45.0\%$ токенов | Проверить адаптеры `lang/` на корректность вырезания тел (`⋮----`) |
| **MCP Tools Latency** | `< 5.0 ms` | Проверить блокирующие синхронные вызовы в `ci-mcp` |
| **Cross-project Compatibility** | 100% PASS | Убедиться в корректности резолвера путей |

---

### Шаг 3. Деплой актуального бинарника на хост

При успешном прохождении тестов обновить хостовый бинарник (с флагом замены занятого inode):

```bash
rtk cargo build --release
install -m 755 target/release/context-init ~/.local/bin/context-init
```

---

### Шаг 4. Синхронизация базы знаний проекта

Перед коммитом убедиться в отсутствии архитектурного дрейфа самого проекта:

```bash
# Проверка
rtk context-init check --compact --exit-code .

# Синхронизация при появлении новых файлов/тестов
rtk context-init update . --compact
```
